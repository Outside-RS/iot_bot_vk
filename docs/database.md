# База данных

PostgreSQL 15. Одиннадцать таблиц. Схему создаёт `reset_db.js`, дополняет
`migrate_update.js`. Расширение `pg_trgm` подключается при создании базы
(`init.sql` для docker-compose, либо вручную: `CREATE EXTENSION pg_trgm`).

Дальше по каждой таблице: зачем она, что в колонках и кто с ней работает.

---

## users — все, кто писал боту

Одна строка на человека ВКонтакте. Здесь же хранится состояние диалога, поэтому
бот не держит ничего в памяти: перезапуск не сбивает разговор.

| Колонка | Тип | Что это |
|---|---|---|
| `vk_id` | BIGINT PK | номер пользователя ВКонтакте |
| `role` | TEXT | `student` или `operator` (администратор). До регистрации пусто |
| `full_name` | TEXT | ФИО студента или имя администратора (из кода доступа) |
| `group_number` | TEXT | номер группы, формат `РИ-240944`. Первая цифра после дефиса — курс |
| `linked_code` | TEXT | код доступа, по которому вошёл администратор (ссылка на `operator_codes`) |
| `state` | TEXT | текущий шаг диалога, см. [bot-flow.md](bot-flow.md) |
| `current_chat_ticket_id` | INTEGER | обращение, в котором человек сейчас переписывается |
| `study_years` | INTEGER | срок обучения, по умолчанию 4 |
| `vk_group_id` | BIGINT | курсовое сообщество студента: по нему переводится курс |
| `is_graduated` | BOOLEAN | выпускник — курс больше не поднимается |
| `ai_context` | JSONB | история диалога с ИИ, до 10 сообщений (5 пар вопрос-ответ) |
| `pending_attachments` | JSONB | фото, присланные до вопроса; прикладываются к обращению |
| `pending_question` | TEXT | последний вопрос студента целиком |
| `notify_tickets` | BOOLEAN | слать ли администратору уведомления о новых вопросах |
| `faq_draft` | JSONB | черновик записи базы знаний до подтверждения администратором |
| `created_at` | TIMESTAMP | когда человек впервые написал боту |

Индекс `idx_users_vk_group` по `vk_group_id` — по нему ищут студентов сообщества
при переводе курса.

**Почему `pending_question` в базе, а не в кнопке.** У ВКонтакте payload кнопки
ограничен 255 символами. Когда текст вопроса клали туда, длинный вопрос делал
кнопку недопустимой и сообщение не отправлялось вообще. Теперь в кнопке только
команда, а текст берётся отсюда.

## vk_groups — подключённые сообщества

| Колонка | Тип | Что это |
|---|---|---|
| `id` | SERIAL PK | внутренний номер |
| `group_id` | BIGINT UNIQUE | номер сообщества ВКонтакте |
| `group_name` | TEXT | название; из него берётся курс |
| `access_token` | TEXT | токен сообщества, от его имени бот отвечает |
| `is_active` | BOOLEAN | подключаться ли при запуске |
| `course` | INTEGER | курс, разобранный из названия. Пусто — не определён |
| `is_archived` | BOOLEAN | сообщество выпускников («… Архив 25/26») |
| `name_synced_at` | TIMESTAMP | когда название последний раз сверяли с ВКонтакте |
| `created_at` | TIMESTAMP | когда добавили |

Курс и признак архива заполняет `courses.js` при добавлении сообщества и при
сверке (`group_sync.js`). Токен — секрет: в панели он показан обрезанным.

## operator_codes — коды доступа администраторов

| Колонка | Тип | Что это |
|---|---|---|
| `code` | TEXT PK | код, который вводят в боте |
| `admin_name` | TEXT | имя; попадает в профиль и в сообщения студентам |

Заводить каждому свой код: имя отсюда подставляется в «Вопрос #12 принят
в работу. Администратор: Алёна». Общий код не даёт понять, кто взял вопрос.

**Роль хранится в `users`, а не здесь.** Удаление кода не отбирает роль у тех,
кто уже вошёл по нему.

## faq — база знаний

| Колонка | Тип | Что это |
|---|---|---|
| `id` | SERIAL PK | номер записи |
| `category` | TEXT | категория; по ней фильтр в панели |
| `question` | TEXT | вопрос студента |
| `answer` | TEXT | ответ бота |
| `keywords` | TEXT | фразы через запятую, помогают поиску |
| `created_at` | TIMESTAMP | когда завели запись |
| `search_vector` | TSVECTOR | поисковый индекс, считается автоматически |

`search_vector` строится из `question` и `keywords` — **ответ в поиске не
участвует**, иначе длинные ответы перетягивали бы на себя любые запросы.

Два индекса: `faq_search_idx` (GIN по `search_vector`) для полнотекстового
поиска и `faq_trgm_idx` (GIN, `gin_trgm_ops`) для поиска по триграммам,
который ловит опечатки.

У записей, заведённых до 19.09.2026, `created_at` пустой: колонку добавили
позже и намеренно не проставили всем одну дату миграции.

## tickets — обращения к администратору

| Колонка | Тип | Что это |
|---|---|---|
| `id` | SERIAL PK | номер обращения, его видят обе стороны |
| `student_vk_id` | BIGINT | кто задал вопрос |
| `vk_group_id` | BIGINT | сообщество, в котором вопрос задан |
| `operator_vk_id` | BIGINT | кто взял в работу; пусто, пока в очереди |
| `question` | TEXT | текст вопроса целиком |
| `status` | TEXT | `open` (в очереди), `active` (в работе), `closed` (завершено) |
| `attachments` | TEXT[] | фото, присланные с вопросом |
| `created_at` | TIMESTAMP | когда создано |

Индексы: `tickets_status_idx` по статусу и `idx_tickets_group_status` по паре
«сообщество + статус» — по нему выбирается очередь конкретного курса.

Обращение забирается одним запросом с условием `status = 'open'`: иначе два
администратора, нажавшие кнопку одновременно, получили бы один вопрос вдвоём.

### Почему у обращения есть сообщество

Бот работает сразу в нескольких сообществах — по одному на курс. Ответить
студенту он может только через то сообщество, которому студент писал: ВКонтакте
не разрешает сообществу писать первым тому, кто с ним не переписывался.

Поэтому обращение помнит своё сообщество, и весь список действий администратора
ограничен им: очередь, мои диалоги, история, взятие вопроса, переписка. Иначе
администратор, состоящий в нескольких курсовых сообществах, мог взять чужой
вопрос из соседнего диалога — его ответы уходили бы от имени не того
сообщества, ВКонтакте отклонял бы их с ошибкой 901, а он об этом не узнавал:
вопрос уже занят и из очереди пропал, студент ждёт ответа, которого не будет.

У обращений, созданных до появления колонки, `migrate_update.js` проставляет
сообщество автора. Если у автора сообщество неизвестно, обращение останется без
него и не попадёт в очередь ни одного курса — скрипт сообщает, сколько таких.

## messages — переписка по обращению

| Колонка | Тип | Что это |
|---|---|---|
| `id` | SERIAL PK | номер сообщения |
| `ticket_id` | INTEGER → tickets | к какому обращению; при удалении обращения удаляются и сообщения |
| `sender_vk_id` | BIGINT | кто написал |
| `text` | TEXT | текст |
| `attachments` | TEXT[] | вложения в формате ВКонтакте (`photo123_456`) |
| `is_read` | BOOLEAN | прочитано ли собеседником |
| `created_at` | TIMESTAMP | когда отправлено |

Из этой переписки собирается черновик записи базы знаний, когда администратор
нажимает «Добавить в базу знаний».

## ai_queue — очередь вопросов к ИИ

| Колонка | Тип | Что это |
|---|---|---|
| `id` | SERIAL PK | номер задачи |
| `vk_id` | BIGINT → users | кто спросил; при удалении пользователя задача удаляется |
| `vk_group_id` | BIGINT | через какое сообщество отвечать |
| `ai_context` | JSONB | история диалога, которая уйдёт в модель |
| `faq_context` | TEXT | подсказки из базы знаний |
| `status` | TEXT | `pending`, `processing`, `error` |
| `attempts` | INTEGER | сколько раз обработка сорвалась |
| `created_at` | TIMESTAMP | когда поставлена в очередь |
| `started_at` | TIMESTAMP | когда взята в работу |

Индекс `idx_ai_queue_status`.

**Очередь в базе, а не в памяти:** перезапуск бота не теряет вопросы. Воркер
берёт задачи через `FOR UPDATE SKIP LOCKED`, поэтому параллельные обработчики
не возьмут одну дважды. Зависшие ищутся по `started_at`, а не по `created_at`:
иначе задача, пролежавшая в очереди дольше таймаута, сбрасывалась бы сразу
после старта и обрабатывалась дважды.

## ai_usage — расход токенов GigaChat

| Колонка | Тип | Что это |
|---|---|---|
| `model_class` | TEXT PK | класс модели: `lite`, `pro`, `max` |
| `model_id` | TEXT | идентификатор модели, например `GigaChat-2-Pro` |
| `tokens_used` | BIGINT | израсходовано токенов |
| `quota` | BIGINT | лимит класса |
| `exhausted` | BOOLEAN | квота выбрана — класс пропускается |
| `updated_at` | TIMESTAMP | последнее обновление |

Во freemium-режиме у каждого класса своя независимая квота. Когда заканчивается
один класс, бот переходит к следующему, а не падает на резервную модель. Цифры
можно сверить с личным кабинетом Сбера кнопкой ↻ в панели.

## app_settings — настройки ИИ

Ровно одна строка: `id BOOLEAN PRIMARY KEY DEFAULT TRUE`. Такой приём не даёт
завести вторую строку настроек.

| Колонка | Что это |
|---|---|
| `ollama_url` | адрес локальной модели |
| `ollama_model` | какая модель Ollama используется |
| `gigachat_key` | ключ авторизации GigaChat |
| `gigachat_scope` | область доступа, обычно `GIGACHAT_API_PERS` |
| `gigachat_model` | предпочитаемая модель GigaChat |

Настройки правятся в панели, на главной — карточка «Настройки ИИ». Из `.env`
значения берутся только при первой установке, если в базе пусто.

## session — сессии входа в панель

Служебная таблица библиотеки `connect-pg-simple`: `sid`, `sess`, `expire`.
Раньше сессии жили в памяти процесса, и любой перезапуск разлогинивал всех.
Истёкшие строки чистятся автоматически раз в 15 минут.

## Скрипты работы со схемой

| Скрипт | Что делает |
|---|---|
| `node reset_db.js` | создаёт схему с нуля и загружает `faq_data.json`. **Удаляет все таблицы**, спрашивает подтверждение — нужно ввести имя базы. Флаг `--yes` пропускает вопрос |
| `node migrate_update.js` | добавляет недостающие колонки и таблицы в существующую базу. Идемпотентный: данные не трогает, можно запускать повторно |
| `node update_faq.js` | **дополняет** базу знаний из `faq_data.json`: запись с тем же вопросом обновляется, остальные остаются. С флагом `--replace` удаляет все записи базы знаний и загружает файл начисто (спрашивает подтверждение, `--yes` пропускает вопрос). Другие таблицы не трогает |

### Как полностью заменить базу знаний

Важно понимать: и `update_faq.js`, и кнопка «Импорт» в панели по умолчанию
**дополняют** базу. Если загрузить новый файл поверх старого, старые вопросы
останутся, и бот продолжит отвечать по ним — для поиска они равноправны с новыми.

Чтобы заменить базу знаний целиком:

```bash
node update_faq.js --replace
```

Скрипт покажет, сколько вопросов сейчас в базе, и попросит подтверждение.
Удаление и загрузка идут одной транзакцией: если файл окажется битым, ничего
не удалится — старая база останется на месте. Обращения, пользователи и
настройки ИИ не затрагиваются, `reset_db.js` для этого не нужен.

В Docker:

```bash
docker compose exec bot node update_faq.js --replace --yes
```

Перед заменой стоит сохранить текущую базу знаний: в панели, раздел «База
знаний» → «Скачать базу».

При обновлении бота на рабочем компьютере запускается **только**
`migrate_update.js`. `reset_db.js` там запускать нельзя — он сотрёт данные.

## Как заглянуть в базу руками

```bash
docker compose exec db psql -U postgres
```

Полезные запросы:

```sql
SELECT count(*) FROM users WHERE role = 'student';        -- сколько студентов
SELECT status, count(*) FROM tickets GROUP BY status;     -- обращения по состояниям
SELECT * FROM ai_queue WHERE status <> 'pending';         -- что застряло в очереди
SELECT model_id, tokens_used, quota FROM ai_usage;        -- расход токенов
```
