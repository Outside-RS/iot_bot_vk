# Перенос и обновление бота на рабочем компьютере

Инструкция для компьютера, на котором бот работает постоянно (ПК в вузе, Windows).
Порядок рассчитан на то, что там уже запущена старая версия.

Схема после переноса:

```
Браузер администратора
        |  https://<IP VPS>
        v
   VPS: frps (порты 80, 443, 7000)
        |  туннель frp
        v
ПК в вузе, docker compose:
   frpc -> caddy (HTTPS) -> bot -> db
                            backup -> копии базы: сюда и на VPS
   Ollama стоит на самом ПК, вне docker
```

Что нужно под рукой: пароль от админки, токен frps (он уже есть в `frpc.toml` на этом ПК),
SSH-доступ к VPS со своего личного компьютера.

Все команды выполняются в папке проекта — там, где лежит `docker-compose.yml`.
Они одинаковы для Git Bash и PowerShell.

### Как найти папку проекта

Гадать не нужно: бот на этом компьютере уже работает, и путь можно спросить у Docker.

```bash
docker ps --format "{{.Names}}"
```

Среди контейнеров будет тот, чьё имя оканчивается на `-bot-1`, например
`vk-bot-search-bot-1`. Спросите у него путь:

```bash
docker inspect vk-bot-search-bot-1 --format "{{index .Config.Labels \"com.docker.compose.project.working_dir\"}}"
```

Команда напечатает полный путь — что-то вроде
`C:\Users\Администратор\Documents\GitHub\iot_bot_vk\vk-bot-search`. Перейдите туда:

```bash
cd "C:/Users/Администратор/Documents/GitHub/iot_bot_vk/vk-bot-search"
```

В Git Bash косые черты пишутся прямыми, даже если Docker напечатал обратные.
Проверьте, что попали куда надо:

```bash
ls docker-compose.yml .env frpc.toml
```

Должны найтись все три файла. Если какого-то нет — это не та папка, дальше идти нельзя.

Она лежит внутри клона репозитория, поэтому `git pull` работает прямо из неё —
переходить в корень `iot_bot_vk` не нужно. Проверить, что это вообще клон:

```bash
git status
```

Если ответит `not a git repository` — это поправимо, см. следующий раздел.

---

### Если папка проекта — не клон репозитория

Так бывает, если бота в первый раз просто скопировали: на рабочем столе лежит папка
`vk-bot-search`, а `git status` отвечает `not a git repository`. Тогда `git pull`
работать не будет, и обновляться придётся копированием файлов вручную — каждый раз.

Это лечится один раз: рядом разворачивается настоящий клон, а секреты переносятся
в него. База при этом никуда не девается — объяснение ниже.

**Почему база сохранится.** Данные лежат не в папке проекта, а в томе Docker с именем
`vk-bot-search_postgres_data`. Имя тома складывается из имени проекта, а оно задано
строкой `name: vk-bot-search` в начале `docker-compose.yml`. Пока эта строка на месте,
Docker найдёт тот же том, откуда бы вы ни запускали `docker compose`.

**Порядок.**

1. В старой папке остановите и удалите контейнеры. Именно `down`, и ни в коем случае
   не `down -v`: с ключом `-v` удаляются тома, то есть база.

   ```bash
   docker compose down
   ```

2. Рядом со старой папкой (например, на том же рабочем столе) сделайте клон:

   ```bash
   git clone https://github.com/Outside-RS/iot_bot_vk.git
   ```

   Появится папка `iot_bot_vk`, а внутри неё — `vk-bot-search` с актуальным кодом.

3. Перенесите в новую папку то, чего нет в репозитории. Это ваши секреты, второго
   экземпляра у них не существует:

   - `.env`
   - `frpc.toml`
   - папку `backups`, если она есть

   Копировать из `vk-bot-search` (старой) в `iot_bot_vk/vk-bot-search` (новую).

4. Перейдите в новую папку и запустите:

   ```bash
   cd iot_bot_vk/vk-bot-search
   docker compose up -d --build
   ```

5. Проверьте, что база на месте: откройте админку и посмотрите, сколько вопросов
   в базе знаний и есть ли пользователи. Если там пусто — остановитесь и не
   продолжайте: значит Docker завёл новые тома, а старые целы и лежат рядом.
   Посмотреть список:

   ```bash
   docker volume ls
   ```

6. Старую папку не удаляйте недели две. Когда убедитесь, что всё работает, удалите —
   но сначала ещё раз сверьтесь, что `.env` и `frpc.toml` перенесены.

Дальше обновление кода делается из новой папки в три команды — порядок важен,
см. раздел 4:

```bash
git pull
docker compose build && docker compose run --rm bot node migrate_update.js
docker compose up -d --build
```

**Важно:** папка с `docker-compose.yml` должна и дальше называться `vk-bot-search`,
а строка `name: vk-bot-search` — оставаться в файле. Переименование папки при
удалённой строке заставит Docker считать это новым проектом: он создаст пустые тома,
бот поднимется с пустой базой, а данные останутся лежать в стороне под старым именем.
Потерять их так нельзя, но напугать это может сильно.

## 1. Подготовка, пока старая версия работает

### 1.1. Резервная копия базы

```bash
docker compose exec -T db sh -c "pg_dump -U postgres -d postgres | gzip > /tmp/before-update.sql.gz"
```

```bash
docker cp "$(docker compose ps -q db):/tmp/before-update.sql.gz" ./before-update.sql.gz
```

Проверьте, что файл `before-update.sql.gz` появился и весит не ноль. Это точка возврата:
из него база восстанавливается целиком (раздел 8).

### 1.2. Проверить, свободен ли порт 443

В этой версии Caddy публикует порт 443 на самом компьютере — так панель
открывается из сети университета и продолжает работать, когда сервер недоступен.
Если порт уже занят чужой программой, обновление прервётся на середине с
ошибкой `port is already allocated`, поэтому лучше проверить заранее:

```bash
netstat -ano | findstr :443
```

Пусто — всё в порядке, идите дальше. Что-то нашлось — номер в последнем столбце
это идентификатор процесса, посмотреть его можно в диспетчере задач на вкладке
«Подробности». Освободите порт либо откажитесь от локального доступа: как —
написано в разделе 5.6.

### 1.3. Запомнить текущую версию кода

```bash
git rev-parse --short HEAD
```

Запишите номер. К нему можно вернуться, если что-то пойдёт не так.

### 1.4. Проверить `.env`

Откройте `.env` в папке проекта. Должны быть заполнены:

| Переменная | Что это | Если её нет |
|---|---|---|
| `DB_USER`, `DB_PASSWORD`, `DB_NAME` | доступ к базе | оставить как было |
| `ADMIN_PASS` | пароль входа в веб-админку | придумать |
| `SESSION_SECRET` | подпись cookie сессии | **новое требование** — без него бот не запустится |

Если `SESSION_SECRET` нет, создайте случайную строку и впишите её:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Добавьте в `.env` ещё три строки:

```
PUBLIC_IP=94.103.86.240
BACKUP_SSH_HOST=94.103.86.240
LOG_TIMEZONE=Asia/Yekaterinburg
```

`PUBLIC_IP` — адрес, по которому открывается админка; на него Caddy получает сертификат.
`BACKUP_SSH_HOST` — куда отправлять копии базы; если оставить пусто, копии будут только
на этом компьютере.

А вот эти две строки, наоборот, нужно **удалить**, если они там есть:

| Переменная | Почему её быть не должно |
|---|---|
| `ENABLE_FRPC` | остаток прежней схемы, когда бот работал прямо на Windows и сам запускал `frpc.exe`. Сейчас туннель — отдельный контейнер. Если строка останется, а кто-то позже запустит `node index.js` напрямую, поднимется второй туннель и подерётся с контейнером за порт 80: в журнале будет `port already used`, а причина совершенно неочевидная |
| `ALLOWED_GROUP_IDS` | ограничитель для локальных тестов. На рабочем компьютере запретит боту подключаться к сообществам, и студенты перестанут получать ответы |

Заодно удалите из папки сам `frpc.exe`, если он там лежит: он больше не нужен,
а его наличие — половина условия для той самой ошибки выше.

Полный список переменных с пояснениями — в `vk-bot-search/.env.example`.
Сам `.env` в репозиторий не попадает и при обновлении кода не перезаписывается.

## 2. Обновление кода

Если папка проекта — клон репозитория:

```bash
git pull
```

Если нет — скопируйте свежую версию папки с заменой файлов, **сохранив** `.env` и `frpc.toml`:
их нет в репозитории, и потерять их нельзя.

---

## 3. Настройка туннеля

Откройте `frpc.toml`. Строки `serverAddr`, `serverPort` и `auth.token` оставьте свои,
а всё остальное замените содержимым `frpc.toml.example` начиная со строки `webServer.addr`.

Должно получиться два прокси: `admin-https` (порт 443, с передачей IP посетителя)
и `admin-panel` (порт 80, без передачи IP — иначе Let's Encrypt не сможет проверить сервер),
а перед ними — две строки `webServer`. Их легко пропустить, но без них не работает
присмотр за туннелем (см. пункт 7): контейнер просто запустится как обычный frpc
и напишет об этом в журнал.

На VPS настраивать ничего не нужно: frps работает в режиме сети host и без ограничений
по портам, файрвол не включён, порт 443 свободен — проверено 16.09.2026.

## 4. Запуск

Порядок важен: **сначала база приводится к новой версии, потом запускается новый
код.** Если сделать наоборот, новый бот какое-то время проработает на старой
схеме, и в это окно студент, создающий обращение, получит ошибку — код уже
обращается к колонкам, которых ещё нет.

**Шаг 1.** Соберите образ, не запуская бота:

```bash
docker compose build
```

Первый раз это займёт несколько минут: скачиваются образы Caddy и PostgreSQL,
собираются образы бота и контейнера копий. Нужен интернет.

**Шаг 2.** Обновите базу разовым запуском:

```bash
docker compose run --rm bot node migrate_update.js
```

`run --rm` поднимет базу, выполнит скрипт в отдельном контейнере и удалит его.
Старый бот в это время продолжает отвечать студентам: миграции только добавляют
колонки и таблицы, ему они не мешают.

Скрипт идемпотентный: данные не трогает, запускать можно повторно.

**Обратите внимание на строки про сообщества.** Их будет две группы.

Первая — про пользователей: скрипт восстанавливает сообщество тем, у кого оно
не записано, по их обращениям и задачам к ИИ. Раньше сообщество запоминалось
только при завершении регистрации, а по нему работает автоматический перевод
на следующий курс: студент без сообщества не переводится, и никто об этом не
узнаёт. Если скрипт сообщит, что часть студентов осталась без сообщества —
ничего делать не нужно, оно запишется само, как только каждый из них напишет
боту.

Вторая — про обращения. В этой версии обращение помнит,
в каком сообществе задан вопрос: очередь и диалоги администратора теперь
ограничены одним курсом. Старым обращениям скрипт проставляет сообщество автора
и печатает, скольким проставил. Если он сообщит, что часть осталась без
сообщества, — у этих студентов сообщество не записано, и такие обращения не
попадут в очередь ни одного курса. Посмотреть их:

```bash
docker compose exec db psql -U postgres -c "SELECT id, student_vk_id, status, left(question, 60) FROM tickets WHERE vk_group_id IS NULL AND status <> 'closed'"
```

Обычно это давно заброшенные вопросы. Если среди них есть живые, проставьте
сообщество вручную, подставив нужный номер из раздела «Группы VK» в панели:

```bash
docker compose exec db psql -U postgres -c "UPDATE tickets SET vk_group_id = -00000000 WHERE id = 42"
```

**Если база пустая** (бот ставится на новый компьютер с нуля), шаг 2 завершится
ошибкой `relation "ai_queue" does not exist` — обновлять ещё нечего. Сначала создайте
схему, а потом повторите шаг 2:

```bash
docker compose run --rm bot node reset_db.js
```

Скрипт спросит подтверждение: нужно ввести имя базы. **На работающем боте его запускать
нельзя** — он удаляет все таблицы вместе с данными.

**Шаг 3.** Запустите всё:

```bash
docker compose up -d --build
```

Отдельных команд для остальных контейнеров не нужно: `up -d` сам пересоздаёт
каждый, у которого изменилась настройка. Например, в этой версии у Caddy
появилась публикация порта 443 — он будет пересоздан автоматически, в выводе
это видно как `Recreate` и `Recreated`. Контейнеры, у которых ничего не
менялось, останутся работать нетронутыми.

## 5. Проверка

### 5.1. Контейнеры

```bash
docker compose ps
```

Подняты должны быть пять: `bot`, `db`, `caddy`, `frpc`, `backup`.

### 5.2. Сертификат HTTPS

```bash
docker compose logs caddy
```

Нужна строка `certificate obtained successfully` со ссылкой на `acme-v02.api.letsencrypt.org`.
После этого откройте `https://94.103.86.240` — браузер не должен ругаться на сертификат.

Если сертификат не выдан, причина будет в этом же логе. Обычно это закрытый порт на VPS
или сеть вуза, которая не пускает к серверам Let's Encrypt. Временное решение — дописать
в `.env` строку `TLS_MODE=internal` и выполнить `docker compose up -d caddy`: HTTPS заработает,
но браузер будет предупреждать о недоверенном сертификате.

### 5.3. Бот

```bash
docker compose logs bot
```

Ожидаются строки `[DB] Подключено к базе`, `[BOT] Бот запущен` для каждого сообщества,
`[WORKER] AI Queue worker запущен`.

### 5.4. Резервные копии

```bash
docker compose logs backup
```

В логе будет строка вида:

```
restrict,command="/usr/local/bin/receive-backup" ssh-ed25519 AAAA... vkbot-backup
```

Скопируйте её целиком — она понадобится в разделе 6.

### 5.5. Админка

Откройте `https://94.103.86.240`, войдите паролем из `ADMIN_PASS` и проверьте:

1. «Группы VK» → кнопка «↻ Сверить все с VK»: курсы сообществ подтянутся из их названий.
2. Личные коды администраторов вместо общего `ADMIN-MAIN` — см. раздел 5.10.
3. На главной появится карточка «Резервная копия» с датой последней копии.

### 5.6. Панель по локальному адресу

В этой версии Caddy публикует порт 443 на самом компьютере, а не только принимает
туннель. Благодаря этому панель доступна из сети университета и продолжает
работать, даже когда сервер недоступен.

Отдельной команды для этого не нужно: `docker compose up -d --build` из раздела 4
видит, что у Caddy изменилась настройка, и пересоздаёт его сам — в выводе будет
`Recreated`. Панель при этом моргнёт на несколько секунд.

Проверьте с другого компьютера в той же сети:

```
https://<адрес рабочего компьютера>
```

Адрес смотрится командой `ipconfig` — строка «IPv4-адрес». Браузер предупредит,
что сертификат выписан на другое имя: он выписан на публичный адрес, и это
ожидаемо. Соединение зашифровано, пароль открытым текстом не ходит.

**Если `docker compose up -d` ругается `port is already allocated`** — порт 443 на
этом компьютере уже кем-то занят. Посмотреть кем:

```bash
netstat -ano | findstr :443
```

Тогда либо освободите порт, либо откажитесь от локального доступа: создайте
`docker-compose.override.yml` со строками, убирающими публикацию:

```yaml
services:
  caddy:
    ports: !reset []
```

### 5.7. Проверка внешнего доступа

Бот сам следит за тем, открывается ли панель снаружи. На главной странице панели
есть карточка «Доступ снаружи» — через пару минут после запуска она должна
показать «работает» и срок действия сертификата.

При пропаже доступа администраторам приходит сообщение в ВКонтакте с адресами,
по которым панель открыта локально, а при восстановлении — второе. Тревога
поднимается со второй неудачной проверки подряд, так что короткий обрыв связи
никого не разбудит.

Частота проверки задаётся в `.env` переменной `EXTERNAL_CHECK_MINUTES`
(по умолчанию 10 минут).

### 5.8. Незавершённые регистрации

Отдельный шаг для этого обновления. Раньше бот не отвечал, если на вопрос
«Кто вы?» человек писал текстом вместо нажатия кнопки: диалог оставался без
кнопок, и продолжить регистрацию было нельзя. Ошибка исправлена, но те, кто на
неё наткнулся, сами об этом не узнают, пока не напишут снова.

Посмотреть, о скольких людях речь:

```bash
docker compose exec bot node remind_registration.js
```

Скрипт ничего не отправляет и ничего не меняет — только показывает список: кому
и от имени какого сообщества написали бы. В списке будут и те, кто просто
бросил регистрацию сам, — отличить одних от других нельзя, да и сообщение
подходит обоим.

Если решите написать:

```bash
docker compose exec bot node remind_registration.js --send
```

Людям придёт сообщение с вопросом «Кто вы?» и кнопками. Ограничить свежими
можно так: `--send --days 30`.

Часть сообщений не дойдёт — это нормально: кто-то запретил сообщения от
сообщества.

У тех, кто писал боту до этого обновления, сообщество в базе не записано:
раньше оно запоминалось только при завершении регистрации, а эти люди до него
как раз и не дошли. Таким скрипт пробует написать от каждого подключённого
сообщества по очереди — пройдёт только то, которому человек писал сам, — и
запоминает найденное. Поэтому в списке у них вместо названия сообщества будет
«перебором из N сообществ», а отправка займёт больше времени.

### 5.9. Бот в VK

Напишите боту из тестового сообщества: задайте вопрос, дождитесь ответа ИИ, нажмите
«Передать администратору» и убедитесь, что вопрос дошёл до администратора.

### 5.10. Личные коды администраторов

Пока в базе есть общий код `ADMIN-MAIN`, роль администратора в боте может получить любой,
кто его введёт: код лежит в исходниках проекта. На главной админки об этом висит красный
баннер. Заменять его на личные коды нужно в таком порядке:

1. На странице «Администраторы» заведите каждому свой код и впишите его имя. Имя из кода
   попадает в профиль и подставляется в сообщения: «Вопрос #12 принят в работу.
   Администратор: Алёна».
2. Попросите администраторов перезайти под своим кодом: в боте «👤 Профиль» →
   «🚪 Выйти из аккаунта», затем написать боту любое сообщение и ввести новый код.
   Тех, кто не перезашёл, удалите на странице «Пользователи» — при следующем сообщении
   боту они пройдут регистрацию заново.
3. Только после этого удалите код `ADMIN-MAIN`.

**Роль хранится в профиле пользователя, а не в коде.** Если просто удалить `ADMIN-MAIN`,
все, кто успел войти по нему, останутся администраторами с именем «Администратор» —
и в уведомлениях будет не видно, кто взял вопрос.

## 6. Резервные копии на VPS

Делается один раз. На VPS уже созданы пользователь `botbackup`, его папка и скрипт приёма
`/usr/local/bin/receive-backup`. Осталось разрешить ключ, который создал контейнер `backup`
(строка из пункта 5.4).

Зайдите на VPS со своего личного компьютера и выполните:

```bash
cat >> /home/botbackup/.ssh/authorized_keys
```

Вставьте строку, нажмите Enter, затем Ctrl+D. После этого:

```bash
chmod 600 /home/botbackup/.ssh/authorized_keys
chown botbackup:botbackup /home/botbackup/.ssh/authorized_keys
```

Проверьте отправку с ПК в вузе:

```bash
docker compose run --rm backup now
```

Ожидаемый ответ: `Копия готова`, затем `принято: ...` и `Копия отправлена на сервер`.

Дальше копии делаются каждую ночь в 03:00: 14 дней хранятся в папке `backups` рядом
с проектом, 30 дней — на VPS.

## 7. Чтобы бот работал без присмотра

Главный риск — не сбой программы, а перезагрузка Windows. Docker Desktop запускается только
после входа пользователя в систему, поэтому после перезагрузки из-за обновлений бот
не поднимется, пока кто-то не войдёт.

1. **Автоматический вход в Windows.** Win+R → `netplwiz` → снять галочку «Требовать ввод
   имени пользователя и пароля» → ввести пароль учётной записи. Если галочки нет, включить
   её видимость: Win+R → `regedit` →
   `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\PasswordLess\Device` →
   параметр `DevicePasswordLessBuildVersion` = 0.
2. **Автозапуск Docker Desktop.** Настройки Docker Desktop → General →
   «Start Docker Desktop when you sign in».
3. **Не уходить в спящий режим.** Параметры → Система → Питание → «Сон» → «Никогда».
   Либо в командной строке от администратора:
   ```
   powercfg /change standby-timeout-ac 0
   powercfg /change hibernate-timeout-ac 0
   ```
4. **Включение после пропадания питания.** В BIOS найти «Restore on AC Power Loss»
   (или «After Power Failure») и выставить «Power On».
5. **Время обновлений Windows.** Параметры → Центр обновления → Период активности:
   выставить рабочие часы, чтобы перезагрузки приходились на ночь.

Контейнеры поднимаются сами: у всех стоит `restart: unless-stopped`. Ollama на Windows
стартует вместе с входом в систему.

За туннелем следит сторож — `frpc-watchdog.sh` внутри контейнера `frpc`. Он нужен потому,
что `restart: unless-stopped` спасает только от падения программы, а frpc после обрыва связи
иногда остаётся жив, но бесполезен: бесконечно повторяет `i/o deadline reached` и не оживает,
даже когда сеть давно вернулась. Со стороны это выглядит так, что бот отвечает студентам,
а админка недоступна. Сторож раз в минуту спрашивает состояние у самого frpc и, если туннель
не работает три проверки подряд, завершает его — Docker поднимает контейнер заново.

Обновлять программы не нужно: версии зафиксированы, сертификат Caddy продлевает сам.
Раз в год можно обновить Caddy:

```bash
docker compose pull caddy && docker compose up -d caddy
```

## 8. Если что-то пошло не так

Этот раздел — для того, кто разбирается в устройстве бота. Короткая инструкция
для тьюторов, оказавшихся рядом с выключенным компьютером, — в
[docs/restart.md](docs/restart.md): включить, дождаться, при необходимости
выполнить одну команду.

### Админка не открывается, а бот отвечает студентам

Почти всегда это туннель. Бот общается с ВКонтакте исходящими запросами и работает
независимо от VPS, поэтому студенты ничего не замечают.

```bash
docker compose logs frpc --tail 30
```

Что бывает видно:

| В журнале | Что это | Что делать |
|---|---|---|
| `start proxy success` | туннель поднят, дело не в нём | проверить `docker compose ps` и логи `caddy` и `bot` |
| `i/o deadline reached`, `connect to server error` | нет связи с VPS | если повторяется больше пяти минут — `docker compose restart frpc` |
| `port already used` | порт на VPS занят другим клиентом frp | убедиться, что старый туннель не работает где-то ещё |
| `[watchdog] перезапуск контейнера` | сторож сам заметил зависание | ничего, он уже всё сделал |
| `[watchdog] ... нет webServer` | в `frpc.toml` пропущены строки `webServer` | добавить их из `frpc.toml.example` и `docker compose up -d frpc` |

Если туннеля нет совсем и сервер недоступен насовсем — это не авария: бот
работает, а панель открыта на самом рабочем компьютере по адресу
`http://localhost:3000`. Что делать дальше — раздел 13, там же варианты без
сервера.

Если туннель в порядке, а панель всё равно не открывается — проверьте сертификат:

```bash
docker compose logs caddy --tail 30
```

При неудаче с сертификатом панель можно временно поднять на своём: в `.env` написать
`TLS_MODE=internal` и выполнить `docker compose up -d caddy`. Браузер будет ругаться на
сертификат, но панель заработает, и можно спокойно разбираться.

### Откат кода

```bash
git checkout НОМЕР_ВЕРСИИ_ИЗ_ПУНКТА_1.3
docker compose up -d --build
```

### Восстановление базы

Бот останавливается, текущая база переименовывается в `postgres_old` — её можно удалить
позже, когда убедитесь, что всё в порядке.

Ниже `postgres` — имя базы; если в `.env` переменная `DB_NAME` другая, подставьте своё.

```bash
docker compose stop bot backup
```

```bash
docker cp ./before-update.sql.gz "$(docker compose ps -q db):/tmp/restore.sql.gz"
```

Отключить оставшиеся подключения к базе — иначе переименовать её не получится:

```bash
docker compose exec -T db psql -U postgres -d template1 -c "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname='postgres' AND pid <> pg_backend_pid()"
```

Переименовать старую базу и создать пустую. Команды выполняются с подключением
к служебной базе `template1`: PostgreSQL не разрешает переименовать базу,
к которой подключён сам, — без этого всё сорвётся на первом же шаге.

```bash
docker compose exec -T db psql -U postgres -d template1 -c "ALTER DATABASE postgres RENAME TO postgres_old"
docker compose exec -T db psql -U postgres -d template1 -c "CREATE DATABASE postgres"
```

Залить копию и запустить бота обратно:

```bash
docker compose exec -T db sh -c "gunzip -c /tmp/restore.sql.gz | psql -U postgres -q -d postgres"
docker compose start bot backup
```

Ошибок при заливке быть не должно. Если их много и они вида
`relation ... already exists` — значит, база не была пустой, и восстановление
нужно начинать заново с шага переименования.

Проверьте, что данные на месте:

```bash
docker compose exec -T db psql -U postgres -c "SELECT count(*) FROM faq"
```

Когда убедитесь, что всё работает, удалите старую базу:

```bash
docker compose exec -T db psql -U postgres -d template1 -c "DROP DATABASE postgres_old"
```

Так же восстанавливается любая ночная копия из папки `backups` или с VPS
(`/home/botbackup/backups`, скачивается командой `scp`).

### Проверить копию, не трогая рабочую базу

```bash
docker cp ./backups/ИМЯ_ФАЙЛА.sql.gz "$(docker compose ps -q db):/tmp/check.sql.gz"
docker compose exec -T db psql -U postgres -c "CREATE DATABASE restore_check"
docker compose exec -T db sh -c "gunzip -c /tmp/check.sql.gz | psql -U postgres -q -d restore_check"
docker compose exec -T db psql -U postgres -d restore_check -c "SELECT count(*) FROM faq"
```

Удалить проверочную базу:

```bash
docker compose exec -T db psql -U postgres -c "DROP DATABASE restore_check"
```

## 9. Что где лежит

| Что | Где |
|---|---|
| Настройки и пароли | `.env` в папке проекта (в репозиторий не попадает) |
| Токен туннеля | `frpc.toml` там же (в репозиторий не попадает) |
| Копии базы | папка `backups` рядом с проектом и `/home/botbackup/backups` на VPS |
| Логи бота | том Docker `bot_logs`; скачиваются в админке на странице «Логи» |
| Сертификат HTTPS | том Docker `caddy_data` |
| Ключ отправки копий | том Docker `backup_keys` |
| Данные базы | том Docker `postgres_data` |

Имена томов начинаются с имени проекта — оно задано строкой `name: vk-bot-search`
в начале `docker-compose.yml`. Поэтому база находится независимо от того, куда
перенесли папку; подробнее — в разделе про клон репозитория выше.

Тома Docker переживают пересборку контейнеров, но удаляются командой `docker compose down -v`.
На рабочем компьютере эту команду выполнять нельзя: она сотрёт базу, сертификат и ключ.

## 11. Обновление базы знаний

Обычный способ — раздел «База знаний» в панели: там добавляют и правят вопросы
по одному, а кнопкой «Импорт» загружают файл JSON. Скрипты нужны, когда меняют
базу целиком или когда панель недоступна.

### Дополнить

```bash
docker compose exec bot node update_faq.js
```

Читает `faq_data.json` из папки бота. Запись с тем же вопросом обновляется,
остальные остаются на месте. То же самое делает кнопка «Импорт» в панели.

### Заменить целиком

**Это не одно и то же.** И скрипт без флага, и кнопка «Импорт» базу *дополняют*.
Если загрузить новый файл поверх старого, старые вопросы никуда не денутся, и бот
продолжит отвечать по ним: для поиска они равноправны с новыми. Заметить это
трудно — база выглядит обновлённой, а бот отвечает старым текстом.

Порядок замены:

1. **Сохраните текущую базу знаний.** В панели: «База знаний» → «Скачать базу».
   Ночная резервная копия тоже есть, но так быстрее и нагляднее.
2. Положите новый `faq_data.json` в папку `vk-bot-search` рядом с `docker-compose.yml`.
   Файл должен быть в UTF-8, массив объектов с полями `category`, `question`,
   `answer`, `keywords`.
3. Выполните:

   ```bash
   docker compose exec bot node update_faq.js --replace
   ```

   Скрипт покажет, сколько вопросов сейчас в базе, и попросит подтверждение —
   ввести слово «удалить». Чтобы обойтись без вопроса, добавьте `--yes`.

Удаление и загрузка идут одной транзакцией: если файл окажется битым, не
удалится ничего и старая база останется на месте. Нумерация вопросов начинается
заново с единицы. Обращения, пользователи и настройки ИИ не затрагиваются —
`reset_db.js` для смены базы знаний запускать не нужно, он сотрёт всё.

После замены проверьте бота: напишите ему пару вопросов из новой базы и
убедитесь, что он отвечает, а не уходит к ИИ.

## 12. Переезд на другой компьютер

Этот раздел — про смену самого компьютера: старый меняют, он сломался или бот
переезжает в другой кабинет. Обновление кода на том же компьютере описано выше,
в разделах 1–5.

Главное, что нужно понимать: **база не лежит в папке проекта**. Она внутри
Docker, в томе `vk-bot-search_postgres_data`. Скопировать папку недостаточно —
на новом компьютере бот запустится с пустой базой.

Переезжает три вещи:

| Что | Откуда взять |
|---|---|
| Код | из репозитория, командой `git clone` |
| Настройки | файлы `.env` и `frpc.toml` из папки проекта |
| База | дамп, который сделаем на старом компьютере |

Логи, сертификат HTTPS и ключ отправки копий не переносятся: логи не нужны,
сертификат новый Caddy получит сам, ключ создастся заново (см. шаг 8).

### 12.1. На старом компьютере: свежая копия базы

```bash
docker compose run --rm backup now
```

Копия появится в папке `backups` рядом с проектом, имя вида
`vkbot-2026-09-23-2100-utc.sql.gz`. Проверьте, что файл создался и весит не
пару байт.

Если контейнер копий не настроен, снимите дамп напрямую:

```bash
docker compose exec -T db pg_dump -U postgres -d postgres | gzip > move.sql.gz
```

### 12.2. Соберите то, что повезёте

- свежий дамп базы;
- `.env`;
- `frpc.toml`.

Больше ничего не нужно: код приедет из репозитория. Не копируйте `node_modules`,
`logs` и старые копии базы.

`.env` и `frpc.toml` — это пароль от панели, ключ GigaChat и токен туннеля.
После переноса удалите их с флешки.

### 12.3. Остановите старого бота

**Обязательный шаг.** Два бота, подключённые к одному сообществу, будут отвечать
студентам по два раза, а два туннеля подерутся за порты на сервере.

```bash
docker compose stop
```

Остановленные так контейнеры не поднимутся сами даже после перезагрузки. Совсем
убрать их можно после успешного переезда (шаг 12.9).

### 12.4. Подготовьте новый компьютер

1. Windows 10 или 11.
2. **Docker Desktop** — с сайта docker.com, при установке согласиться на WSL 2.
3. **Git** — с git-scm.com.
4. Проверьте, что Docker запустился: значок в трее и зелёная надпись
   *Engine running* в окне программы.

Node.js ставить не нужно: бот собирается внутри Docker.

### 12.5. Заберите код

```bash
git clone https://github.com/Outside-RS/iot_bot_vk.git
```

```bash
cd iot_bot_vk/vk-bot-search
```

### 12.6. Положите настройки

Скопируйте в эту папку `.env` и `frpc.toml` со старого компьютера. Менять в них
ничего не нужно — адреса, пароли и токены остаются прежними.

Проверьте, что оба файла на месте:

```bash
ls .env frpc.toml
```

### 12.7. Поднимите базу и залейте копию

Сначала только база — бот пока не нужен:

```bash
docker compose up -d db
```

Подождите полминуты, пока PostgreSQL создаст пустую базу, и залейте дамп
(подставьте имя своего файла):

```bash
docker cp ./move.sql.gz "$(docker compose ps -q db):/tmp/restore.sql.gz"
```

```bash
docker compose exec -T db sh -c "gunzip -c /tmp/restore.sql.gz | psql -U postgres -q -d postgres"
```

База новая и пустая, поэтому переименовывать и удалять ничего не нужно — в
отличие от восстановления на работающем боте (раздел 8).

Проверьте, что данные приехали:

```bash
docker compose exec -T db psql -U postgres -c "SELECT (SELECT count(*) FROM faq) AS вопросов, (SELECT count(*) FROM users) AS пользователей, (SELECT count(*) FROM tickets) AS обращений"
```

Числа должны совпадать с теми, что были на старом компьютере.

### 12.8. Запустите всё остальное

```bash
docker compose build && docker compose run --rm bot node migrate_update.js
```

```bash
docker compose up -d --build
```

Первая сборка занимает несколько минут и требует интернета. Порядок тот же, что
в разделе 4: сначала схема, потом код. Здесь это не так важно — бот ещё никому
не отвечает, — но привычка полезная.

### 12.9. Проверьте и уберите за собой

1. Пройдите раздел 5 целиком: контейнеры, сертификат, бот, копии, админка,
   бот в VK.
2. **Новый ключ резервных копий.** Контейнер копий создал на новом компьютере
   свой ключ — его нужно добавить на VPS по разделу 6, а строку старого ключа
   из `~botbackup/.ssh/authorized_keys` удалить.
3. **Настройте автономную работу** по разделу 7: автоматический вход в Windows,
   автозапуск Docker, запрет сна, включение после пропадания питания.
4. Убедитесь, что панель открывается по HTTPS и сертификат выдан. Если за
   неделю переезжать несколько раз, Let's Encrypt может отказать: у него лимит
   в пять одинаковых сертификатов в неделю. Тогда временно поставьте в `.env`
   `TLS_MODE=internal` — панель будет работать с предупреждением браузера.
5. Когда всё проверено, на старом компьютере уберите контейнеры и настройки:

```bash
docker compose down
```

Затем удалите `.env` и `frpc.toml` — в них пароли и токены.

Саму папку и тома Docker на старом компьютере лучше не трогать ещё пару недель:
это ваш запасной вариант, если на новом что-то всплывёт.

## 13. Смена сервера

Сервер (VPS) в этой схеме делает ровно одно: принимает запросы к админке и
передаёт их по туннелю на рабочий компьютер. Бот общается с ВКонтакте сам,
исходящими запросами, и от сервера не зависит.

Поэтому потеря сервера — не авария. Студенты ничего не заметят.

### 13.1. Что происходит, когда сервера нет

| Что | Состояние |
|---|---|
| Бот, ответы студентам, обращения | работают как обычно |
| Админка снаружи | недоступна |
| Админка на самом рабочем компьютере | **работает**: `https://localhost` и `http://localhost:3000` |
| Админка из сети университета | **работает**: `https://<адрес этого компьютера>` |
| Копии базы рядом с проектом | делаются как обычно |
| Копии на сервер | не уходят, в журнале ошибки |
| Сертификат HTTPS | не продлевается: проверка идёт через туннель |

Главное отсюда: **панель не «переключается» на локальный доступ — он есть всегда**,
параллельно с внешним. Caddy слушает порт 443 не только со стороны туннеля, но и
на самом компьютере, поэтому:

- с рабочего компьютера — `https://localhost` (или `http://localhost:3000` в обход
  Caddy);
- из сети университета — `https://` и адрес этого компьютера, узнать его можно
  командой `ipconfig`.

Пароль везде тот же. Браузер при заходе по локальному адресу предупредит, что
сертификат выписан на другое имя — так и есть, он выписан на публичный адрес.
Соединение при этом зашифровано.

Поэтому ничего переключать не нужно: пропал сервер — тьюторы в вузе продолжают
работать по адресу компьютера, а вы узнаете о пропаже из сообщения бота.

Чтобы не засорять журнал бесконечными попытками подключиться, туннель можно
остановить:

```bash
docker compose stop frpc
```

Запускать обратно — `docker compose start frpc`.

### 13.2. Вариант А. Новый VPS

Подходит, если нужен доступ к панели из интернета. Требования к серверу
минимальные: 1 ядро, 1 ГБ памяти, белый IP. Российский хостер удобнее — до него
лучше связь из университетской сети.

**Шаг 1.** На новом сервере установите Docker:

```bash
curl -fsSL https://get.docker.com | sh
```

**Шаг 2.** Создайте конфигурацию frps. Токен придумайте новый, длинный и
случайный — он единственное, что защищает туннель от посторонних:

```bash
mkdir -p /root/frp
```

```bash
cat > /root/frp/frps.toml <<'EOF'
bindPort = 7000
auth.method = "token"
auth.token = "ПРИДУМАЙТЕ_ДЛИННЫЙ_ТОКЕН"
EOF
```

**Шаг 3.** Запустите frps:

```bash
docker run -d --name frps --network host --restart always -v /root/frp/frps.toml:/etc/frp/frps.toml snowdreamtech/frps:latest
```

Сеть `host` здесь обязательна: frps сам открывает порты 80 и 443 для туннелей,
и пробрасывать их по одному не нужно.

**Шаг 4.** Проверьте, что порт слушается и ничто его не закрывает:

```bash
ss -tlnp | grep 7000
```

```bash
iptables -L INPUT -n | head -3
```

Если в фаерволе есть правила — разрешите входящие на 7000, 80 и 443.

**Шаг 5.** На рабочем компьютере поправьте два файла.

В `frpc.toml` — адрес и токен нового сервера:

```toml
serverAddr = "НОВЫЙ_IP"
auth.token = "ТОТ_ЖЕ_ТОКЕН_ЧТО_НА_СЕРВЕРЕ"
```

В `.env` — новый адрес в двух местах:

```
PUBLIC_IP=НОВЫЙ_IP
BACKUP_SSH_HOST=НОВЫЙ_IP
```

**Шаг 6.** Пересоздайте контейнеры, которые их читают:

```bash
docker compose up -d caddy frpc backup
```

Именно `up -d`, а не `restart`: переменные окружения попадают в контейнер при
создании.

**Шаг 7.** Дождитесь нового сертификата — он выдаётся на новый адрес:

```bash
docker compose logs caddy --tail 30
```

Ждём `certificate obtained successfully`. Старый сертификат остаётся лежать в
томе и никому не мешает.

**Шаг 8.** Восстановите отправку копий: на новом сервере нужны пользователь
`botbackup`, скрипт приёма и ключ рабочего компьютера — всё по разделу 6.

**Шаг 9.** Пройдите проверку по разделу 5.

### 13.3. Вариант Б. Без сервера, по сети университета

Подходит, если доступ к панели нужен только внутри вуза: тьюторы и так сидят в
этой сети. Сервер при этом не нужен вовсе, платить не за что.

**Что получится:** панель открывается по адресу вида `https://10.х.х.х` с
рабочего компьютера и с любого компьютера университетской сети. Браузер будет
ругаться на сертификат — он самоподписанный; предупреждение придётся принять
один раз.

**Шаг 1.** Узнайте адрес рабочего компьютера в сети университета:

```bash
ipconfig
```

Нужна строка «IPv4-адрес» активного подключения — что-то вроде `10.2.15.40`.
Попросите сетевую службу закрепить этот адрес за компьютером, иначе после
перезагрузки роутера он изменится и панель «переедет».

**Шаг 2.** Порт 443 Caddy уже опубликован в основном `docker-compose.yml`, так
что панель по адресу компьютера работает и без всяких правок. Остаётся выключить
туннель, чтобы он не ломился на несуществующий сервер. Создайте рядом с
`docker-compose.yml` файл `docker-compose.override.yml`:

```yaml
services:
  frpc:
    profiles: [ "tunnel" ]
```

С таким профилем `docker compose up -d` туннель больше не поднимает. Compose
подхватывает файл с этим именем автоматически, команды остаются прежними.

**Шаг 3.** В `.env` укажите адрес компьютера и внутренний сертификат:

```
PUBLIC_IP=10.2.15.40
TLS_MODE=internal
BACKUP_SSH_HOST=
```

`TLS_MODE=internal` обязателен: Let's Encrypt не выдаёт сертификаты на адреса
локальной сети. Пустой `BACKUP_SSH_HOST` выключает отправку копий на сервер —
они продолжат делаться в папку `backups`, и их стоит иногда копировать на
флешку или в облако вручную.

**Шаг 4.** Примените:

```bash
docker compose up -d
```

При первом запуске Windows спросит, разрешить ли Docker принимать подключения
из сети — разрешите для частной сети.

**Шаг 5.** Проверьте с другого компьютера в той же сети: `https://10.2.15.40`.

Не открывается — почти всегда дело в брандмауэре Windows либо в том, что сеть
университета изолирует компьютеры друг от друга. Второе решается только через
сетевую службу.

### 13.4. Вариант В. Через роутер, проброс порта

Подходит, если бот стоит не в вузе, а там, где есть свой роутер и белый IP от
провайдера.

**Сначала проверьте, есть ли белый IP.** На рабочем компьютере:

```bash
curl ifconfig.me
```

Сравните полученный адрес с тем, что показан в настройках роутера как WAN или
«внешний адрес». Совпадают — белый IP есть. Отличаются — провайдер держит вас
за общим адресом (NAT), и проброс работать не будет: нужен либо другой тариф,
либо вариант А.

**Что сделать:**

1. В настройках роутера закрепить за компьютером постоянный локальный адрес
   (по MAC-адресу).
2. Пробросить на него порты 443 и 80. Порт 80 нужен не для панели, а для
   проверки Let's Encrypt.
3. Создать `docker-compose.override.yml` как в варианте Б — туннель здесь тоже
   не нужен. Порт 80 понадобится пробросить и в Docker: добавьте туда же
   `caddy: { ports: [ "80:80" ] }`, иначе проверка Let's Encrypt не пройдёт.
4. В `.env` указать `PUBLIC_IP=ВНЕШНИЙ_IP`, а `TLS_MODE` не задавать — здесь
   сертификат будет настоящий.
5. `docker compose up -d` и проверить сертификат по логам Caddy.

**Чем это хуже сервера:** внешний адрес у домашних провайдеров обычно меняется,
и после смены перестанут работать и адрес, и сертификат. И рабочий компьютер
оказывается открыт в интернет напрямую, без прослойки в виде сервера.

### 13.5. Что меняется в любом случае

| Файл | Строка | Когда менять |
|---|---|---|
| `.env` | `PUBLIC_IP` | всегда: это адрес, на который выдаётся сертификат |
| `.env` | `TLS_MODE` | `internal` для локальной сети, иначе не задавать |
| `.env` | `BACKUP_SSH_HOST` | новый сервер или пусто, если сервера нет |
| `frpc.toml` | `serverAddr`, `auth.token` | только при смене VPS |
| `docker-compose.override.yml` | целиком | только когда туннель не нужен |

После правок — обязательно `docker compose up -d`, а не `restart`.

И отдельно: смена адреса означает новый сертификат. Let's Encrypt разрешает не
больше пяти одинаковых сертификатов в неделю на один адрес, так что метаться
между вариантами несколько раз за день не стоит. Упёрлись в лимит — поставьте
`TLS_MODE=internal`, панель будет работать с предупреждением браузера, пока
лимит не отпустит.
